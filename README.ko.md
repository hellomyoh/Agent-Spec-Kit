# README.md — Agent 기반 프로젝트 초기화 / 개발 프롬프트 사용 가이드

[English](README.md) | **한국어**

> 이 문서는 영문 `README.md`의 한국어 번역본입니다. 파일 참조는 정식 이름(`AGENTINIT.md`, `KICKOFF.md`, `DEVELOPINIT.md`)을 사용합니다.

이 문서는 `AGENTINIT.md`, `KICKOFF.md`, `DEVELOPINIT.md`를 Codex, Claude Code, Cursor Agent 등에서 사용하는 방법을 설명하는 **프레임워크(템플릿) 사용 설명서**입니다. 이 `README.md`는 agentinit 템플릿 저장소의 README이며, 사람이 읽는 참조용입니다.

> **사용 방식 (clone 후 복사):**
> 이 템플릿 저장소를 clone한 뒤, **`AGENTINIT.md` / `KICKOFF.md` / `DEVELOPINIT.md` 3개 파일만 본인 프로젝트 저장소로 복사**하세요.
> 이 `README.md`(가이드)는 템플릿 저장소에 그대로 두고, 본인 프로젝트로 복사하지 않습니다.
> agentinit 템플릿 저장소에 직접 push하지 마세요. 작업은 본인 프로젝트 저장소에서 진행합니다.
> 이렇게 하면 본인 프로젝트에서 초기화 시 생성되는 **프로젝트 `README.md`** 와 이 가이드가 서로 충돌하지 않습니다(서로 다른 저장소에 있으므로).

> **중요:** `AGENTINIT.md`에는 반드시 사용자의 프로젝트 개요, 러프한 요구사항, 핵심 기능, 제약사항을 작성해야 합니다. Agent는 이 내용을 기준으로 기능명세서, 횡단 계약 문서, 개발 계획을 생성합니다.
>
> 초기 설정 단계에서 프로젝트 목적, 대상 사용자, MVP 기능, 데이터, 외부 연동, 인증/권한, QA 기준 등이 모호하면 Agent는 임의로 추측하지 않고 사용자에게 질문하여 요구사항을 명확히 해야 합니다.

## 0. 이 버전에서 강화된 점 (요약)

기존 구조의 약점을 보완하기 위해 다음이 추가/변경되었습니다.

| 강화 항목 | 내용 |
|---|---|
| `ARCHITECTURE.md` 신설 | 데이터 모델·네이밍·API 계약·인증 모델 등 **여러 기능에 공통 적용되는 계약**을 한 곳에 모으고, 모든 개발 세션에서 항상 로드 → 기능 간 일관성 확보 |
| `adr/INDEX.md` 신설 | ADR 목록 인덱스. 선택적 로딩 세션이 관련 설계 결정을 싸게 발견 |
| ADR 필수화 | 지정된 트리거(아키텍처/인증/DB/외부 API/배포 등)에서는 ADR 작성이 재량이 아니라 **필수** |
| 코드-명세 불일치 규칙 수정 | "무조건 명세를 고친다"가 아니라 **먼저 어느 쪽이 권위인지 진단** → 구현 실수의 사후 정당화 방지 |
| PROGRESS 잠정 기록 | `다음 세션 첫 명령`을 작업 **시작 시점에 잠정 기록** → 중단되어도 연속성 유지 |
| 원자적 commit | 코드 변경과 대응 문서 변경을 **하나의 commit**으로 묶음 |
| HISTORY 회전 | 이력이 길어지면 압축·아카이브하여 컨텍스트 부담 완화 |
| 기능 입도 가이드 | feature 단위 기준과 MVP 기능 수 권장치(3~7개) 제시 |
| 가정 충돌 점검 | 새 가정 기록 전 기존 가정/ARCHITECTURE와 충돌 여부 확인 |
| CLAUDE.md 강화 | 한 줄 참조 대신 **항상 지킬 핵심 규칙**을 함께 탑재 |
| 테스트 실증 | "테스트 통과"는 **실제 실행 + 결과 기록** 시에만 인정 |
| 멀티에이전트 감사 흔적 | feature 문서에 참여 Agent·주요 위험 **1~3줄 요약**을 남겨 검토 누락 방지 |
| AI 위임 마커 | 사용자가 모르는 항목에 `[AI 위임]`을 적으면, 비핵심은 기본값 진행·핵심은 보수적 잠정 결정 + 보고서에서 검토 권장 |
| 가이드/프로젝트 README 분리 | 가이드 `README.md`는 템플릿 저장소에 두고, 본인 프로젝트에는 프롬프트 3종만 복사 → 프로젝트의 생성 `README.md`와 충돌 없음 (clone 후 복사 방식) |

## 1. 기본 파일 구성

agentinit 템플릿 저장소는 아래 구성입니다.

```text
agentinit/  (템플릿 저장소 — clone 대상)
├── README.md         # 이 가이드(영문). 본인 프로젝트로 복사하지 않음
├── README.ko.md      # 이 가이드의 한국어 번역본. 본인 프로젝트로 복사하지 않음
├── AGENTINIT.md      # 사용자가 작성하는 프로젝트 요구사항 입력 문서
├── KICKOFF.md        # 초기화용 프롬프트
└── DEVELOPINIT.md    # 개발 진행용 프롬프트
```

이 저장소를 clone한 뒤, **`AGENTINIT.md` / `KICKOFF.md` / `DEVELOPINIT.md` 3개 파일만 본인 프로젝트 저장소로 복사**하세요. (`README.md` 가이드는 복사하지 않습니다.)

```text
my-project/  (본인 프로젝트 저장소 — 여기서 작업)
├── AGENTINIT.md      # 템플릿에서 복사
├── KICKOFF.md        # 템플릿에서 복사
└── DEVELOPINIT.md    # 템플릿에서 복사
```

사용자는 초기화 실행 전에 `AGENTINIT.md`에 프로젝트 요구사항을 먼저 작성해야 합니다.

가능한 범위에서 아래 내용을 작성하세요.

- 프로젝트 목적
- 대상 사용자
- 핵심 기능 (입도 가이드: 한 기능 = 한 사용자 가치, MVP 3~7개 권장)
- MVP에 반드시 포함할 기능
- 후순위 기능
- 외부 API / 외부 시스템
- 저장하거나 분석해야 할 데이터
- 화면 / UX 요구사항
- 인증 / 권한 요구사항
- **횡단(아키텍처) 기준선** (데이터 모델 공통 규칙, 네이밍, API 계약 스타일, 인증 모델)
- 테스트 / QA 요구사항
- 운영 / 배포 제약사항

각 파일의 역할은 다음과 같습니다.

| 파일 | 역할 |
|---|---|
| `README.md` (템플릿) | 프레임워크 사용 설명서(이 문서). 템플릿 저장소에 두고 본인 프로젝트로 복사하지 않음 |
| `AGENTINIT.md` | 사용자가 작성하는 프로젝트 요구사항 입력 문서 (복사 대상) |
| `KICKOFF.md` | 프로젝트 초기화용 프롬프트 (복사 대상) |
| `DEVELOPINIT.md` | 초기화 이후 실제 개발 진행용 프롬프트 (복사 대상) |

> 참고: 본인 프로젝트에서 초기화 후 생성되는 **프로젝트 `README.md`** 는 이 가이드와 같은 이름이지만 다른 저장소에 있는 다른 문서입니다.
> 가이드는 "에이전트를 구동하는 법", 프로젝트 README는 "이 프로젝트가 무엇이고 어떻게 실행하는지"를 다룹니다.

## 2. 최초 1회: 프로젝트 초기화 프롬프트

`AGENTINIT.md` 작성을 완료한 뒤, Agent에 아래 프롬프트를 입력합니다.

```text
AGENTINIT.md와 KICKOFF.md를 읽고, KICKOFF.md의 지시에 따라 프로젝트 초기 설정을 진행하세요.

AGENTINIT.md는 사용자가 작성한 프로젝트 요구사항입니다.
KICKOFF.md는 초기화 작업 지시서입니다.

반드시 다음을 수행하세요.

1. AGENTINIT.md를 분석하세요.
2. 프로젝트 초기화에 필요한 핵심 요구사항이 충분한지 확인하세요.
3. 프로젝트 목적, 대상 사용자, MVP 기능, 사용자 시나리오, 데이터, 외부 연동, 인증/권한, QA 기준이 모호하면 초기화를 진행하기 전에 사용자에게 질문하세요.
4. 질문이 필요한 경우 한 번에 최대 5개 이내로 핵심 질문만 작성하세요.
5. 여러 기능에 공통 적용되는 계약(데이터 모델/네이밍/API/인증)을 정리하여 ARCHITECTURE.md를 생성하세요.
6. KICKOFF.md의 절차에 따라 프로젝트 구조와 문서를 생성하세요.
7. features/, docs/, qa/, adr/ 문서를 생성하세요. adr/INDEX.md를 포함하세요.
8. AGENTS.md, ARCHITECTURE.md, PLAN.md, PROGRESS.md, HISTORY.md, ASSUMPTIONS.md, CLAUDE.md를 생성하세요.
8-1. 프로젝트 README.md(소개·설치·실행·구조·문서 링크)를 생성하세요. 민감 정보는 넣지 마세요.
9. feature 문서는 Multi-Agent 검토 결과를 바탕으로 작성하되, Agent별 발언록이 아니라 최종 합의된 기능명세서로 작성하고, 참여 Agent와 주요 위험을 1~3줄로 요약하세요.
10. QA는 feature별 테스트 시나리오와 qa/ 폴더의 회귀/수동/릴리즈 체크리스트로 분리하여 작성하세요. "테스트 통과"는 실제 실행 시에만 인정한다는 기준을 포함하세요.
11. 초기화가 끝나면 생성한 파일 목록, ARCHITECTURE 요약, 기능명세서 목록, QA 문서 목록, ADR 목록, 개발 Phase 요약, 다음 개발 시작 명령을 보고하세요.
```

이 프롬프트는 **프로젝트 초기 세팅 전용**입니다.
이 단계에서는 실제 구현을 시작하지 않고, 개발을 시작하기 위한 문서와 계획을 생성합니다.

> 초기화는 단계가 길어 중간에 끊길 수 있습니다. Agent는 각 단계가 끝날 때마다 `PROGRESS.md`의 초기화 진행 상태를 갱신하므로, 끊기면 같은 프롬프트로 이어서 진행하면 됩니다.

## 3. 초기화 단계에서 요구사항이 모호한 경우

초기화 단계에서는 요구사항 품질이 중요합니다.
다음 항목이 모호하면 Agent가 임의로 추측하지 않고 사용자에게 질문해야 합니다.

- 프로젝트 목적 / 대상 사용자 / MVP 핵심 기능 / 핵심 사용자 시나리오
- 외부 API / 외부 시스템 연동 목적
- 저장하거나 분석해야 할 데이터
- 민감정보 / 개인정보 / 보안 요구사항
- 인증 / 권한 / 관리자 기능
- 데이터 모델·인증 모델의 큰 방향 (ARCHITECTURE 기준선)
- 테스트 / QA 기준
- 배포 환경 / 운영 제약
- MVP와 후순위 기능 구분

반대로 파일명, 폴더 구조, 코드 스타일, 일반 테스트 도구, 로컬 개발 환경 구성, **네이밍 세부 표기 규칙** 같은 세부 기본값은 사용자에게 묻지 않고 `ASSUMPTIONS.md`(또는 `ARCHITECTURE.md`)에 기록한 뒤 진행합니다.

질문 예시:

```text
프로젝트 초기화를 위해 확인이 필요합니다.

AGENTINIT.md를 분석한 결과, 초기 기능명세서와 개발 계획을 만들기 전에 아래 내용을 확인해야 합니다.

1. 이 프로젝트의 MVP에서 반드시 포함해야 하는 기능 3가지는 무엇인가요?
2. 주요 사용자는 일반 사용자, 관리자, 운영자 중 누구인가요?
3. 외부 API 연동 시 인증 방식과 호출 주기는 어떻게 되나요?

답변을 주시면 그 내용을 반영하여 초기화를 계속 진행하겠습니다.
```

### 3.1 모르는 항목은 AI에게 위임 (`[AI 위임]`)

답을 잘 모르거나 결정하기 어려운 항목은 비워두는 대신 `[AI 위임]`(별칭 `[AI에게 맡김]`, `[모름]`)을 적으면 됩니다. Agent는 위험도에 따라 다르게 처리합니다.

- **비핵심 항목**(네이밍, 코드 스타일, 비핵심 UI, 로그 포맷 등): 합리적 기본값으로 진행하고 `ASSUMPTIONS.md`에 기록합니다. 질문하지 않습니다.
- **핵심 항목**(MVP 범위, 데이터 모델, 인증/권한, 개인정보, 외부 연동 등): 초기화를 멈추지 않고, **가장 보수적이고 되돌리기 쉬운 선택**을 잠정 채택한 뒤 `ASSUMPTIONS.md`에 기록하고, 초기화 보고서의 **"AI 위임으로 결정한 항목 (검토 권장)"** 에 모아 표시합니다. 사용자는 나중에 확인·수정할 수 있습니다.

다만 두 가지는 위임할 수 없습니다. **프로젝트 목적과 핵심 기능을 둘 다 비우거나 위임하면**("이 프로젝트가 무엇인지" 자체가 없으면) Agent는 위임을 받지 않고 질문합니다. 또 **비용·결제·법적 영향·되돌리기 어려운 동작**이 걸린 항목은 위임돼도 조용히 결정하지 않고 보수적 기본값을 택한 뒤 확인을 요청합니다.

개발 단계에서도 동일합니다. 프롬프트에서 "이건 알아서 해줘"라고 위임하면 그 항목의 자율 판단 범위가 넓어지되, 핵심 항목은 보수적으로 결정하고 `ASSUMPTIONS.md`와 완료 보고에 남깁니다.

## 4. 초기화 완료 후 생성되는 문서

초기화가 완료되면 일반적으로 아래와 같은 구조가 생성됩니다.

```text
/
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── ARCHITECTURE.md
├── PLAN.md
├── PROGRESS.md
├── HISTORY.md
├── ASSUMPTIONS.md
├── features/
│   ├── README.md
│   └── *.md
├── docs/
│   ├── README.md
│   └── *.md
├── qa/
│   ├── README.md
│   ├── regression-checklist.md
│   ├── manual-test-cases.md
│   └── release-checklist.md
└── adr/
    ├── INDEX.md
    └── *.md
```

각 문서의 역할은 다음과 같습니다.

| 파일 / 폴더 | 역할 |
|---|---|
| `README.md` | **프로젝트 README**(산출물). 프로젝트 소개·설치·실행·구조·문서 링크. push 단위로 갱신 |
| `AGENTS.md` | Agent가 매 실행마다 참조하는 작업 지시서 |
| `CLAUDE.md` | Claude Code 자동 로드 파일. AGENTS.md 참조 + 항상 지킬 핵심 규칙 |
| `ARCHITECTURE.md` | **횡단 계약**(데이터 모델/네이밍/API/인증). 모든 개발 세션에서 항상 로드 |

## 6. 개발 중 사용자에게 질문하는 기준

개발 단계에서는 Agent가 사소한 구현 판단마다 사용자에게 질문하지 않습니다.
이미 생성된 `AGENTS.md`, `ARCHITECTURE.md`, `PLAN.md`, `PROGRESS.md`, `features/*.md`, `qa/*.md`를 기준으로 자율적으로 진행합니다.

사용자에게 질문하는 경우는 **기존 기획의도와 완전히 다른 결정이 필요한 경우**로 제한합니다.

- 기존 MVP 범위 변경
- feature 목적과 다른 방향의 기능 변경
- 핵심 UX 흐름의 큰 변경
- 데이터 모델의 근본적 변경
- 인증 / 권한 / 보안 정책 변경
- 개인정보 / 민감정보 처리 방식 변경
- 외부 API / 외부 시스템 연동 방식 교체
- 배포 구조 / 운영 방식의 큰 변경
- **ARCHITECTURE.md 횡단 계약의 변경**
- 비용 / 결제 / 법적 영향 발생 가능성
- 되돌리기 어려운 데이터 삭제 / 파괴적 변경

그 외 내부 함수명, 파일 위치, 테스트 데이터, mock 데이터, 비핵심 UI 배치, 작은 리팩터링, QA 체크리스트 보완 등은 묻지 않고 진행하며, 필요한 경우 `ASSUMPTIONS.md`에 기록합니다(기존 가정과 충돌 점검 포함).

## 8. QA 진행 방식

QA는 두 단계로 관리합니다.

```text
features/*.md
→ 기능별 테스트 시나리오

qa/*.md
→ 전체 회귀 테스트 / 수동 QA / 릴리즈 체크리스트
```

개발 중에는 다음을 확인합니다.

1. 현재 feature 문서의 테스트 시나리오 확인
2. 자동 테스트 작성
3. 자동 테스트 **실제 실행** (실행 명령·결과 캡처)
4. 실패한 테스트 수정
5. 회귀 테스트 영향 검토
6. 수동 QA 필요 여부 판단
7. 필요한 경우 `qa/manual-test-cases.md` 갱신
8. 테스트 실행 결과 / QA 결과를 `HISTORY.md`와 `PROGRESS.md`에 기록

> "테스트 통과"는 테스트를 실제로 실행하고 결과를 기록했을 때만 인정합니다. 배포·릴리즈 작업이 포함되면 `qa/release-checklist.md`를 확인합니다.

### 8.1 프로젝트 README.md 갱신 (push 단위)

프로젝트 `README.md`는 "이 프로젝트가 무엇이고 어떻게 설치·실행하는지"를 담는 산출물입니다.

- **생성**: 초기화 시 KICKOFF가 `ARCHITECTURE.md` / `features/` / `PLAN.md`를 바탕으로 초안을 만듭니다.
- **갱신 시점**: 매 commit이 아니라 **push 단위에서 갱신 필요 여부를 점검**합니다. 다음이 바뀌었으면 같은 원자적 커밋에 README 변경을 포함합니다.
  - 프로젝트 소개 / 기능 목록 (새 feature 완료 등)
  - 설치 / 실행 / 빌드 방법, 의존성, 환경변수 **이름**(값/Secret은 절대 기재 금지)
  - 프로젝트 구조, 주요 문서 링크(docs/ 등)
  - `ARCHITECTURE.md`의 사용자 노출 사항(예: 지원 환경)
- **갱신 불필요**: 내부 리팩터링, 테스트 전용 변경, 비핵심 UI 미세 조정 등 사용자·설치·실행에 영향이 없으면 README를 건드리지 않습니다.
- README는 항상 로드하는 기준 문서가 아니라 **파생 산출물**입니다. 진실의 출처는 `ARCHITECTURE.md`/`features/`이며, README는 그것을 요약·링크합니다.

## 9. 일관성 유지 메커니즘 (이 버전의 핵심)

기능과 세션이 늘어나도 개발 방향이 흔들리지 않도록 다음을 사용합니다.

```text
ARCHITECTURE.md   → 모든 기능에 공통되는 계약을 한 곳에. 매 세션 항상 로드.
adr/INDEX.md      → 중요한 결정의 목록. 선택적 로딩 세션이 관련 결정을 싸게 발견.
PROGRESS(잠정 기록) → 세션이 끊겨도 다음 세션이 정확히 이어받음.
원자적 commit      → 코드와 문서가 항상 같은 상태로 남음.
권위 진단 규칙      → 코드-명세 불일치를 임의로 지우지 않음. 표류 방지.
HISTORY 회전       → 이력을 잃지 않으면서 컨텍스트 부담을 관리.
```

핵심 원칙: **공통 결정은 ARCHITECTURE.md에, 중요 결정은 ADR에, 진행 상태는 PROGRESS에, 이력은 HISTORY에.** feature 문서에는 그 기능 고유의 명세만 둡니다.

## 12. 핵심 원칙

- `AGENTINIT.md`는 초기화 입력 문서이며, 반드시 프로젝트 요구사항을 작성합니다.
- 초기화 단계에서 핵심 요구사항이 모호하면 Agent는 사용자에게 질문합니다.
- 초기화 이후 실제 개발 기준은 `AGENTS.md`, `ARCHITECTURE.md`, `PLAN.md`, `PROGRESS.md`, `features/*.md`, `qa/*.md`입니다.
- **여러 기능에 공통되는 결정은 `ARCHITECTURE.md`에 두고 매 세션 로드합니다.** feature 문서에 흩어 적지 않습니다.
- 개발 단계에서는 사소한 구현 판단마다 묻지 않고, 기획의도와 완전히 다른 결정이 필요할 때만 질문합니다.
- `features/*.md`는 Agent별 발언록이 아니라 최종 합의된 기능명세서이며, 검토 요약(참여 Agent·주요 위험)을 포함합니다.
- 중요한 설계 결정은 `adr/*.md`로 분리하고 `adr/INDEX.md`를 갱신합니다(지정 트리거는 필수).
- 코드-명세 불일치는 임의로 명세를 고쳐 지우지 말고, 먼저 권위를 진단합니다.
- "테스트 통과"는 실제 실행 + 결과 기록 시에만 인정합니다.
- PROGRESS의 다음 세션 첫 명령은 작업 시작 시 잠정 기록하고 종료 시 최종화합니다.
- 의미 있는 작업 단위가 끝나면 코드+문서를 하나의 commit으로 묶어 commit/push 합니다.
- 가이드 `README.md`는 agentinit 템플릿 저장소에만 두고 본인 프로젝트로 복사하지 않습니다. 본인 프로젝트의 `README.md`는 초기화 시 생성되는 별개의 산출물이며, push 단위로 사용자·설치·실행·아키텍처 영향 시 갱신합니다.
- `main` / `master` 직접 push는 금지하며, Secret·인증서·개인키·토큰 파일은 commit하지 않습니다.
