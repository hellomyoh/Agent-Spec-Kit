# ASK-QBench 중규모+ 확장 설계 (B4–B6)

> 방법론: [METHODOLOGY.md](METHODOLOGY.md) · 소규모 결과: [FINAL_REPORT.md](FINAL_REPORT.md)
> 이 문서는 **중급 이상 규모의 프로젝트**에서 ASK의 효과성을 *입증하도록* 설계한 벤치마크 항목(B4–B6)과 실행 계획이다.

---

## 0. 전제와 가설

**확정된 전제 (소규모):** 단발·소규모 코딩에서 ASK는 baseline 대비 객관적 우위가 없고 토큰만 더 쓴다(B1·B2에서 확인). 이는 제작자 권장(ASK는 **중급 이상** 프로젝트용)과 일치하는 *타당한* 결론이다. 따라서 본 확장의 목적은 "ASK가 항상 좋다"가 아니라 **"규모가 커지면 ASK의 비용이 이득으로 전환되는 지점이 존재하는가"** 를 정량적으로 검증하는 것이다.

**핵심 가설 (Crossover Hypothesis):**
ASK의 **비용은 거의 고정적**(SSOT/ARCHITECTURE/HISTORY 유지 오버헤드)이지만, **이득은 프로젝트 규모에 따라 증가**한다(재발견 비용 절감·교차모듈 회귀 방지·결정 일관성). 따라서 규모를 키우면 **순효과가 음(비용 손해)에서 양(순이득)으로 뒤집히는 임계점(crossover)** 이 나타난다.

이 가설은 반증 가능하다: 임계점이 없거나, 통제군(plan-then-code)이 모든 규모에서 ASK와 같으면 가설 기각.

## 1. ASK가 중규모+에서 효과를 낼 *메커니즘* (측정 대상)

| # | 메커니즘 | ASK 산출물 | 규모와 함께 커지는 이유 |
|---|---|---|---|
| M1 | **교차모듈 회귀 방지** | ARCHITECTURE 계약(모듈 경계·불변식) | 모듈이 많을수록 한 변경이 다른 모듈을 깨기 쉬움 |
| M2 | **교차절단 계약 준수** | ARCHITECTURE의 프로젝트 전역 규약 | 기능이 늘수록 규약 위반 누락 빈도↑ |
| M3 | **재발견 비용 절감** | SPEC·PROGRESS(압축된 현재 상태) | 코드베이스가 클수록 전체 재독해 비용↑, 요약 가치↑ |
| M4 | **결정 일관성** | ASSUMPTIONS·HISTORY(append-only) | 세션이 길수록 과거 결정을 잊거나 모순될 위험↑ |
| M5 | **변경 국소성** | 모듈 책임 분해 | 좋은 분해일수록 변경이 적은 파일에 한정 |

소규모에선 이 메커니즘이 발현될 표면(모듈 수·세션 수·코드량)이 없어서 이득이 0이었다. 중규모+는 그 표면을 만든다.

## 2. 벤치마크 항목 (B4–B6)

### B4 — 다모듈 진화 (Multi-Module Evolution)
- **프로젝트**: 5~15개 모듈이 **공유 계약**으로 엮인 중규모 라이브러리/서비스(아래 §3).
- **흐름**: 골격에서 시작해 **8~15 세션**에 걸쳐 기능 추가·리팩터·요구 변경. 세션마다 새(fresh) 에이전트가 디스크로 인계받음(B2·B3와 동일).
- **측정**: M1(교차모듈 회귀율), M2(계약 위반 수), M5(변경 국소성·churn·결합도/사이클 증가), 누적 정확성, 비용.
- **그룹**: B(baseline, 레포만) / P(plan-then-code, 무구조 노트, compute 정합) / **ASK**(SPEC+ARCHITECTURE+ASSUMPTIONS+HISTORY+PROGRESS).

### B5 — 결정 충돌 함정 (Decision-Conflict Trap) ⭐ ASK 고유효과 검정
- B4 위에 **의도적 함정**을 심는다: 초기 세션에서 확립된 결정을, 후반 세션의 요구가 *암묵적으로 위반하기 쉽게* 만든다.
- 예) 세션 2: "기간은 **초 단위 정수**로 저장"으로 결정 → 세션 9: "5분 스누즈 추가" 요구(순진한 구현은 분 단위를 섞어 계약 위반). 은닉 테스트가 단위 일관성을 검사.
- ASK는 ASSUMPTIONS/HISTORY에 결정을 보존 → 준수 기대. baseline은 큰 코드베이스에서 과거 결정을 놓쳐 위반 기대.
- **측정**: 결정 위반율(seeded trap 통과 여부). 이것이 ASK의 *구조적 기억*이 단순 노트/무기억보다 나은지를 가르는 핵심 지표(소규모 B3에서 분리 못 했던 "구조 vs 노트"를 규모로 분리).

### B6 — 비용-규모 곡선 (Cost-vs-Scale Crossover) ⭐ 헤드라인
- **같은 프로토콜을 규모 3구간에서 반복**: S(≈200 LOC/3모듈) · M(≈1,000 LOC/8모듈) · L(≈3,000 LOC/15모듈).
- 각 구간에서 `ASK − baseline`의 **순토큰 비용**과 **품질 델타**(회귀·계약·정확성)를 측정.
- **예측(가설)**: 비용 델타는 S에서 양(ASK 손해) → M에서 축소 → L에서 음(ASK 순이득). 품질 델타는 S≈0 → M·L에서 양·증가. **임계점(crossover)이 곧 "이 규모 이상에서 ASK 권장"의 정량적 근거.**
- 이 곡선이 제작자 권장("중급 이상")을 **수치로 입증하거나 반증**한다.

## 3. 프로젝트 코퍼스 설계 (결정적 오라클 확보)

중규모에서도 채점이 결정적이려면 **공개 계약을 세션마다 고정**하고 **교차절단 불변식을 자동 검사**해야 한다. 아래 아키타입이 적합:

**아키타입 A — 식(expression) 툴킷** (교차절단 함정이 자연스러움)
- 모듈: lexer · parser · AST 노드 · evaluator · type-checker · pretty-printer · simplifier · REPL.
- **교차절단 계약**: "**모든 AST 노드 타입은 모든 visitor(evaluator/printer/checker/simplifier)에서 처리돼야 한다.**" 새 노드 타입 추가 = 여러 모듈을 동시에 건드리는 변경 → visitor 누락 시 교차모듈 회귀. ASK의 ARCHITECTURE가 "갱신해야 할 visitor 목록"을 명시 → 누락 감소 기대.
- 은닉 테스트: 각 (노드 타입 × visitor) 조합을 검사 → 누락이 결정적으로 잡힘.

**아키타입 B — 미니 이슈/작업 트래커 코어** (계약·결정 함정이 자연스러움)
- 모듈: model · validation · storage · query · permission · serialization · command API.
- **교차절단 계약**: 모든 쓰기는 permission 경유, 모든 응답은 `Result{ok,value,error}` 봉투, 모든 엔티티는 audit 필드, ID 형식 고정.
- **결정 함정(B5)**: 단위·ID 형식·정렬 규칙 등 초기 결정을 후반 요구가 위반하기 쉽게 배치.

**규모 구간(B6)**: 같은 아키타입을 모듈 수/기능 수로 S/M/L 인스턴스화. 각 구간 ≥8 프로젝트(서로 다른 도메인 변형)로 검정력 확보.

각 인스턴스 구성: `repo/`(골격), 세션별 `change_requests/`, 세션별 `hidden_tests/`(기능+계약 검사), `oracle/`(레퍼런스), `contract_checks/`(AST 기반 교차절단 검사기), `seeded_decisions.md`(B5 함정 정의, 비공개).

## 4. 그룹 정의 (compute·메모리 정합, 격리)

| 그룹 | 인계 운반물 | 분리하는 것 |
|---|---|---|
| **B** baseline | 레포(코드)만 | 기준선 |
| **P** plan-then-code | 레포 + 자유형식 노트(분량은 ASK 문서량에 정합) | "기억·계획 일반효과" |
| **ASK** | 레포 + SPEC·ARCHITECTURE(계약)·ASSUMPTIONS·HISTORY(append-only)·PROGRESS | "구조적 SSOT의 순효과" |

- 세션마다 fresh 에이전트, **파일시스템 격리(P8)**: 작업공간에 현재 레포 + 그 그룹의 기억만. 이전 세션 코드/요청서는 인계된 것 외 접근 차단.
- compute 회계(P2): 그룹별 토큰·호출수 기록. P와 ASK의 기록 분량을 맞춰 "구조 vs 분량" 교란 제거.
- 모델: 천장 회피(P4)를 위해 중간 강도 모델 + 약 모델 병행. (강 모델이 대형 과제도 무회귀로 처리하면 약 모델로 변별.)

## 5. 지표 (객관 우선)

| 지표 | 정의 | 도구 |
|---|---|---|
| **교차모듈 회귀율(M1)** | 세션 N에서 *다른 모듈* 테스트가 깨진 비율 | pytest(모듈별 P2P) |
| **계약 위반 수(M2)** | 교차절단 불변식 위반 건수 | AST 기반 contract_checks |
| **재발견 비용(M3)** | 세션에서 *첫 편집 이전*에 쓴 입력 토큰·도구 호출 수(오리엔테이션 비용) | 텔레메트리 |
| **변경 국소성(M5)** | 기능당 touched 파일 수·churn, 결합도/사이클 증가(Martin I·D 델타) | git diff·AST |
| **결정 위반율(B5)** | seeded 결정 함정 통과 여부 | 함정별 은닉 테스트 |
| **누적 정확성·복원** | 최종 기능 통과율, 롤백 복원 충실도 | pytest |
| **순비용(B6)** | 총 토큰; 규모별 `ASK − baseline` | 텔레메트리 |

헤드라인: **B5 결정 위반율**(ASK 고유효과)과 **B6 crossover 곡선**(규모 임계점).

## 6. 통계·사전등록

- 혼합효과 `지표 ~ 그룹 × 규모 + (1|프로젝트) + (1|세션)`; cluster bootstrap(프로젝트 단위). crossover는 규모를 연속/순서형으로 두고 `그룹 × 규모` 상호작용 검정.
- 1차 비교(사전등록): **(a) B5에서 `ASK − max(B, P)` 결정 위반율 감소, (b) B6에서 `그룹 × 규모` 상호작용이 유의(규모가 커질수록 ASK 유리).**
- 효과 **입증 조건**: M/L 구간에서 ASK가 plan-then-code(P) 대비 (교차모듈 회귀 ↓ 또는 계약 위반 ↓ 또는 재발견 비용 ↓)에서 유의, compute 정합 후 유지, ≥8 프로젝트, **그리고 소규모 null이 재현**(crossover 입증).
- 효과 **미주장**: P가 모든 규모에서 ASK와 동률(구조 무효), crossover 없음(오버헤드가 끝까지 미상쇄), 천장으로 변별 불가, 검정력 부족 중 하나.

## 7. ASK 효과를 *입증하도록* 설계된 결정적 테스트 (요약)

1. **교차절단 누락 테스트(B4)**: 새 노드 타입/엔드포인트 추가 후, *모든* visitor/계약 준수를 검사 → ASK의 ARCHITECTURE 계약이 누락을 줄이는지.
2. **결정 충돌 함정(B5)**: 초기 결정과 충돌하는 후반 요구 → ASK의 ASSUMPTIONS/HISTORY가 위반을 막는지(무기억·노트 대비).
3. **재발견 비용(B4/M3)**: 대형 레포에서 *첫 편집 전* 토큰을 그룹 간 비교 → ASK의 SPEC/PROGRESS가 오리엔테이션을 줄이는지.
4. **롤백 복원(B3 확장)**: 다모듈 상태를 이전 마일스톤으로 복원 → 구조적 이력의 충실도.
5. **Crossover 곡선(B6)**: S/M/L에서 순비용·품질 델타 → 임계점 존재 여부.

## 8. 타당성·비용 (정직)

- **고비용**: 다모듈 프로젝트 × 8~15 세션 × 3그룹 × 시드 × 3규모 = 수백 에이전트 런 + 인스턴스(레포·세션별 은닉테스트·계약검사기·오라클) 제작이 무겁다. 본 문서는 **설계**이며, 실행은 단계적으로 한다.
- **오라클 문제**: 다모듈 행위의 결정적 채점이 어렵다. 완화책 — 세션마다 공개 API/계약을 고정(테스트 결착), 교차절단은 **AST 정적 검사기**로 결정적 측정, 기능은 property/differential 테스트.
- **천장·격리·검정력**: P4(난도/모델)·P8(격리)·≥8 프로젝트를 반드시 적용. 미적용 시 소규모 때처럼 변별 실패.

## 9. 단계적 실행 계획

1. **파일럿(권장 첫 단계)**: 아키타입 A(식 툴킷) **1개 프로젝트, M 규모(≈8모듈), 6세션**, 3그룹(B/P/ASK), 2시드 + **B5 함정 1개**. 목표: (a) 교차모듈 회귀·계약 위반·재발견 비용에 *변별 분산*이 생기는지 확인(천장 점검), (b) 파이프라인·격리·계약검사기 검증.
2. **B5 확장**: 함정 3~5개로 결정 일관성 변별력 확보.
3. **B6 곡선**: 같은 아키타입을 S/M/L로 인스턴스화해 crossover 측정.
4. **확충**: 아키타입 B 추가, 프로젝트 ≥8, 중·약 모델 2조건, 혼합효과 분석.

> 결론 방향: 본 설계의 성공 기준은 "ASK가 항상 우월"이 아니라 **"규모 임계점 이상에서 ASK가 plan-then-code 대비 교차모듈 회귀·계약 위반·재발견 비용을 유의하게 줄이고, 소규모 손해가 대형에서 순이득으로 전환된다"** 를 정량적으로 *입증하거나 반증*하는 것이다. 어느 쪽이든 제작자 권장의 적용 범위를 데이터로 규명한다.
